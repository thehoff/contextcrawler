Third independent review pass, four parallel agents by app scope: security core,
command filters, analytics/discovery/parser, and runtime-data mining. Prior
audit passes: #100 (Codex), #111 (Claude). Verdict: the security *plumbing* is
solid; the gaps are a soft centre in permission matching and one missed
ecosystem. The bigger story is operational — the binary crashes daily and
headline token savings are oversold.

## Top tier — fix first

| ID | Severity | Finding |
|---|---|---|
| P0-crash | operational | 33 SIGABRT crashes in 7 days, daily, on the current binary. ~30–100ms process lifetime ⇒ Rust panic in the startup path (an `unwrap()`/`expect()` against the no-unwrap rule). Symbolicate, reproduce with `RUST_BACKTRACE=1`, fix. Suspect: `core/config.rs`, `core/tracking.rs` (DB open), `hooks/` init. |
| P0-grep | operational | `grep` filter's clap parser rejects standard flags (`-q -r -E -i -c -A -B`) → 1,255 parse-failures, 62% of all 2,016. Delivered savings only 10.3% on 17.4M tokens — worst filter in the suite. |
| SEC-C1 | CRITICAL | `dotnet` has no argv deny-list checker on any of its 4 run paths (`dotnet_cmd.rs:34,78,119`). MSBuild `-p:CustomBefore*Targets=<path>` / `CustomAfter*` and `dotnet test --runsettings <file>` are unguarded RCE flags — the same class #111 closed for `go -toolexec`. Fix: add `check_forbidden_dotnet_args`, wire into all 4 paths. |
| SEC-C2 | CRITICAL | Command substitution bypasses the permission/gate stack. `discover/lexer.rs` tokenises `` ` ``/`(`/`)` but `split_on_operators` never decomposes a `$(...)`, backtick, or `<(...)`/`>(...)` payload into its own segment, so `echo $(rm -rf /tmp/x)` evades a `Bash(rm -rf)` deny rule. Fix: lexer surfaces substitution payloads as first-class segments, or `check_command` fails closed on unparsed substitution. |
| SEC-C3 | CRITICAL | Permission rules are byte-prefix matched (`permissions.rs:224-251`). `git  push  --force` (double space), quoting, or `--force=` evade a deny rule. Fix: tokenise both command and pattern via `shell_split`, compare token sequences. |

## Runtime data — measured reality

- **Blended token savings: 53.4%** (61.4M saved / 74.3M input, 14,789 commands, window 2026-04-25 → 05-21). Below the advertised 60–90%.
- Delivering: `cargo` 66.5% (25.4M input — largest sink, working), `find` 73.9%, `ls` 72.2%.
- Underperforming: `read` 13.7%, `grep` 10.3%, `git` 32.2% (`git log` 1.9%), `curl` 2.6% (77/90 runs zero), `gh` 24.4%, `pytest` 13.2%.
- Supply-chain gate: 5,279 records, 99.5% no-op; logs 5,252 `skip` lines → 11.5MB JSONL noise. `RecentRelease` 3-day cooldown false-positives on mainstream packages (`requests`, `@types/node`); `UnvettableSource` false-positives on running an already-installed local plugin. `KnownVulnerability` blocks (pinned vulnerable `requests`/`urllib3`) are correct and valuable.
- Tirith gate: 48 downgrades, no clear false positives. The homoglyph catch is genuinely good — blocked a Cyrillic-`і` `github.com` lookalike, 5 rules, 24ms. Keep it.
- `err` wrapper writes 564 junk `parse_failures` rows (`cmd_ok2_*`, error `"err"`) — test DB likely leaking into the production DB.

## Feature / uplift ideas

- `gain --weak-filters` — rank tools by `input_tokens × (1 − savings)` ("where tokens leak"); `gain --failures` — render the ranked weakness map from `parse_failures`. Data is already collected.
- Missing filters with real volume: `ps` (1.7M tokens passthrough), `rsync`, `du`, `log show`. Route `rg` → existing grep filter (trivial).
- `learn` could auto-generate TOML `match_output`/`replace` filter suggestions from frequent correction rules — close the detection→DSL loop.
- Stop logging supply-chain `skip` records; cache `ccusage` (slow npm subprocess) with a TTL.
- Token-aware permission matching + substitution-aware lexer decomposition (SEC-C2/C3) close an entire evasion class.
- Integrity for the binary-command era — hash/verify the `settings.json` hook registration.

## Method

Four read-only agents, app-scoped, run in parallel; findings consolidated here.
No code changes were made by the review. Severity is the reviewer's assessment;
"CRITICAL" = exploitable or correctness-breaking, "P0" = operational urgency.
