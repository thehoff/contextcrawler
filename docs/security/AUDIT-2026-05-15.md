# Audit record — 2026-05-15

Snapshot of the security review session that produced the v0.1.5
release. Preserves the empirical findings and decisions made so they
don't have to be reconstructed from git log later.

## Scope reviewed

- ContextCrawler `develop` at `bfe32f1` (pre-release tip) through
  `068357c` (post-merge of three security branches).
- Upstream rtk `develop` at HEAD as of fetch time (~913 commits
  ahead of our fork point).
- Upstream GitHub issue **rtk-ai/rtk#640** ("I asked claude --effort
  high to do a security review of contextcrawler") — the canonical record of
  upstream's known findings and their disposition.

## Approach

Three Codex peer-review passes against each of three security feature
branches, plus an empirical fork-vs-upstream comparison done by reading
code (not just diffing commit subjects — the SHA-delta approach was
misleading because upstream commits had been carried forward into the
fork under different SHAs via the `feat-hook-engine` merge work).

## What we did NOT do (and why)

- **Re-sign existing commits with the new GPG/SSH key.** The user
  decided to ship forward unsigned and start signing new commits going
  forward, since rewriting history would invalidate the file:line
  references in the three GHSA advisories already filed.
- **Publish the GHSAs.** They are filed as drafts on
  `thehoff/contextcrawler`. Publication is a separate step (request
  CVE, set publication date, push public advisory) deferred until the
  user is ready to coordinate disclosure.
- **Open PRs.** PR titles like "fix(security): argv-mode default for
  err/test/summary" make the attack-surface narrative public before
  the advisory is published. The branches were pushed but PRs were
  deliberately held back.
- **Address the 544 non-regex `.unwrap()` calls in production.** Out
  of scope for a security release. Tracked in
  `docs/quality/BASELINE.md` for incremental cleanup.

## Methodology notes for future audits

Two lessons saved to project memory during this session:

- **Don't trust commit-subject grep when auditing fork vs upstream.**
  SHA-delta `git log ^HEAD origin/develop` lies when commits are
  carried forward under different SHAs. Authoritative answer comes
  from reading the file at the call site.
- **Check upstream issues, not just commits.** The most security-
  relevant upstream content is in `gh issue list --state all --search
  "security"` — closed-by-design and tracking-only issues are the real
  delta, not merged PRs.
