## Q1: Shell vs Rust for the rule application sub-script
Rust is the right choice for the rule engine. Section 5 explicitly leaves `scripts/branding-apply-rules.sh` as a shell helper and even hints at a Rust binary if TOML parsing “gets complex” (design §5, lines 247-250, 364-375), but this is already a complexity case: the schema allows literal and regex rules, per-rule scope, and `safe_guard` regexes (design §3, lines 106-127). A shell parser here is brittle in exactly the way this design says it must not be. Recommendation: make the apply-rules helper a small Rust binary, build it once at install/CI time, and keep the merge-time path as a direct binary invocation. Do not add `cargo build` to the driver hot path.

## Q2: Line-number stability under length-changing substitutions
The current diff-aware scheme is only safe if every replacement is single-line and newline-free. Section 4a builds the changed-line set from raw line numbers in `%A` and `%B` and then writes back only those lines (design §4a, lines 195-207), but Section 10 already calls out the drift problem if a rule changes line count (design §10, lines 651-654). As written, the schema does not forbid multiline replacements, so the line-number map can go stale. Recommendation: validate at load time that every `needle`/`replacement` pair is line-local, reject any rule that introduces or removes `\n`, and treat multiline edits as out of scope for this driver.

## Q3: Conflict-marker handling
The doc’s current answer is wrong. It says conflict-marker lines are included in the changed-line set and the driver still substitutes inside them, then exits 0 (design §4a, lines 205-207; §10, lines 655-658). That is too clever for a merge driver whose top risk is silent corruption. `UPSTREAM_REBASE.md` makes the human resolve conflicts first and only then re-run verification on the merged file (docs/contributing/UPSTREAM_REBASE.md:107-126). Recommendation: do not rewrite anything inside `<<<<<<<`/`=======`/`>>>>>>>` blocks. Either skip those hunks entirely and leave the file conflicted, or fail closed if the helper cannot isolate the safe regions. Do not touch the markers themselves.

## Q4: safe_guard scope (per-rule vs global)
Keep `safe_guard` per-rule in TOML, but keep the truly structural exclusions global in code. The design already distinguishes narrow per-rule guards like `RTK_MD\b|LEGACY_RTK_MD` from hardcoded no-touch classes for env-var-shaped identifiers and hook-protocol literals (design §4c, lines 223-243). That split is correct. A global TOML table would be too blunt and would hide rule-specific intent; the tests in `branding_lint.rs` show why, because they rely on narrow allowlists and explicit exclusions rather than one coarse bypass (tests/branding_lint.rs:60-104, 174-193). Recommendation: per-rule `safe_guard` stays, and the global “never touch” classes remain hardcoded prefilters, not user-editable TOML.

## Q5: Driver invocation cost during git rebase (per-commit replay)
Do not special-case rebase. The runbook already expects both light rebases every 1–2 weeks and heavier merges only occasionally (docs/contributing/UPSTREAM_REBASE.md:85-113, 159-168), so this path will run often. The driver therefore has to be cheap enough that per-commit replay is irrelevant: parse the rule file once, apply a small set of line-local substitutions, exit. Recommendation: keep the merge driver stateless and O(changed lines), and move any expensive validation out of the hot path. If the helper needs compilation, compile it at install time, not during each replayed commit.

## Diff-Aware Approach
Section 4a is not sound as written. It unions line numbers from `%O→%A` and `%O→%B`, but those are two different coordinate systems; the design never explains how `%B` line numbers are mapped back onto `%A` before substitution (design §4a, lines 195-205). That can work only if the change set is line-local and length-preserving, which the schema does not guarantee. The upside is real: it avoids rewriting allowlisted legacy lines that `branding_lint.rs` intentionally exempts (tests/branding_lint.rs:139-193). The fix is simple: either derive the target spans from the merged file only, or add a real mapping pass and ban multiline edits.

## Single Source of Truth
The direction is right: TOML should be authoritative, and the lint backstop should validate that it stays in sync (design §6, lines 379-446). I agree with rejecting codegen here. But the current asymmetry is too loose: `FORBIDDEN_TOKENS` can drift forever as long as it contains extra historical entries, which makes it easy to forget which rows are actually driver-managed. Recommendation: keep TOML as the source of truth, but mark lint-only rows explicitly or add a second assertion for the literal, auto-fixable subset. Right now the design prevents TOML drift downward, not semantic drift between the driver and the backstop.

## Silent-Corruption Risks
The biggest miss is atomicity in the apply-rules path. Section 5 requires restoring `%A` on non-zero exit and backs it up before writing (design §5, lines 275-277, 328-340), but it never requires the helper itself to write via temp file plus rename. A successful exit after a partial or logically wrong in-place rewrite is still silent corruption. The second miss is conflict content: rewriting inside unresolved hunks can preserve markers while altering the user’s conflict context, which is worse than leaving the file untouched. The third is shell parsing of TOML; if you keep bash in the loop, escaped strings and regexes will eventually bite you.

## TOML Schema Gotchas
The schema is under-specified for a load-bearing config file. Section 3 defines `schema_version`, `continue_on_match`, `type`, `scope`, `safe_guard`, and `id`, but it never states whether duplicate `id`s are illegal, whether `needle`/`replacement` may contain newlines, or what exact regex dialect `safe_guard` must use (design §3, lines 106-127). That matters because Section 4b makes rule order load-bearing, and Section 6 keys the equivalence test off literal `needle` values (design §4b, lines 211-221; §6, lines 393-446). Recommendation: make the loader reject duplicate ids, duplicate literal needles in the same scope, and any newline-bearing replacement unless multiline support is explicitly designed.
